================================================================================
0. OBJETIVO
================================================================================

Correr el ciclo de vida completo de una misión de AgentCity
(https://api.agentcity.dev, NETX testnet, chain id 587) de forma
automatizada: autenticación de wallets, registro on-chain de agentes,
creación de misión, formación de equipo, deliberación, cotización,
acuerdo EIP-712, pago de escrow, ejecución de nodos DAG, y (cuando el
backend público lo permita) cierre económico y liquidación on-chain.

El ciclo YA ESTÁ IMPLEMENTADO Y PROBADO en este repo. Tu trabajo en el
homelab es: (a) replicarlo tal cual, (b) mantenerlo vigilando los fallos
de plataforma conocidos, y (c) opcionalmente extenderlo (backend propio,
nuevos casos de uso) una vez el ciclo base funcione.

6. LOS DOS SISTEMAS DE EJECUCIÓN DE NODOS — USA EL CORRECTO
================================================================================

AgentCity tiene DOS sistemas paralelos para ejecutar los nodos del DAG de
una misión. Son fáciles de confundir; usa el correcto desde el principio:

  SISTEMA A — Collaboration (/api/collaboration/* + MCP tools
  bind_node_service/route_node_task/etc., scripts/agent-city/
  collab-node-runner.mjs): NINGUNA misión completada revisada en la
  testnet compartida lo usa. Es un callejón sin salida a día de hoy
  (bloqueado por el Fallo D, ver §7).

  SISTEMA B — NeurIPS-nativo (/api/neurips/nodes/{live_node_id}/*,
  scripts/agent-city/neurips-node-runner.mjs): este es el que SÍ usan
  las misiones que llegan a liquidarse on-chain de verdad. Cada nodo del
  workflow de la propuesta ganadora tiene un campo `live_node_id`
  (GET /api/teams/mission/{missionId}/proposals →
  workflow.nodes[].live_node_id) que mapea a este sistema.

  Máquina de estados (estricta, cada paso 409 si te lo saltas):
    Idle → route → Invoked → commit{output_hash} → Committed → guard
    → Guarding → verifying → Verifying → verify/tier1 (side-effect)
    → gated → Gated → record → Recording → complete → Completed

  USA SIEMPRE EL SISTEMA B (neurips-node-runner.mjs) salvo que estés
  investigando específicamente el sistema A por curiosidad.

7. FALLOS DE PLATAFORMA CONOCIDOS — NO LOS REDESCUBRAS
================================================================================

Estado a 2026-08-06. Antes de "arreglar" algo, comprueba aquí si ya es un
fallo de backend catalogado (no del cliente). Detalle técnico completo en
docs/playbook-api-completo.md.

  FALLO A — chain-service de signing-payload/eip712-payload (agreement).
    Síntoma: 500 INTERNAL_ERROR.
    Estado: RECUPERADO 2026-07-26 (~8 días caído). No debería reaparecer,
    pero si ves 500 aquí de nuevo, es un fallo de plataforma, no tuyo.

  FALLO B — actions/{complete,release}/payload y rate/payload.
    Síntoma: 500 INTERNAL_ERROR en TODO tipo de misión (confirmado con
    equipo y con misión simple de 2 agentes).
    Estado: ROTO, activo desde 2026-07-18. Compruébalo así:
      curl -X POST -H "Authorization: Bearer $TOKEN" \
        -d '{}' https://api.agentcity.dev/api/missions/{id}/actions/complete/payload
      200 = recuperado. 500 = sigue roto.

  FALLO C — Investment Vault: vault/create/payload, vault/mock-setup.
    Síntoma: 502 crudo / 500 INTERNAL_ERROR. La creación de misión con
    investment_config SÍ funciona; solo falla instanciar el vault.
    Estado: ROTO desde 2026-07-27.

  FALLO D — governance chain_node_id nunca se asigna a los nodos del DAG.
    Bloquea tanto finalize_node (sistema A) como el worker de
    asentamiento automático (sistema B):
      GET /api/dev/settlement/{missionId}/journal
      → "step":"binding_wait",
        "last_error":"waiting for settlement mission binding:
         governance chain_node_id is missing"
    Estado: INTERMITENTE. El worker reintenta solo cada ~10s — cuando se
    recupera, la liquidación ocurre SIN que relances nada manualmente.
    No es necesario ni deseable "arreglarlo" tú mismo; solo espera/vigila.

  FALLO E — Bootstrap de actores del Hosted Demo.
    Se dispara con la tool MCP start_investor_demo({requestId}) —sin
    wallet ni token, ver §9—. Falla en la fase actors_ready:
      {"code":"HOSTED_SMOKE_FAILED","message":"Smoke exited code=1 signal=none"}
    A diferencia de B/D, retryable:false — no se autorepara, pide
    operator_review.
    Estado: INTERMITENTE, descubierto 2026-08-06.

  IMPORTANTE: cuando cualquiera de estos se recupere, NO necesitas
  relanzar nada complejo — para B: relanza mission-flow.mjs (su sección
  10 hará complete/release/rate). Para D: no hagas nada, el worker
  liquida solo. Regenera la trazabilidad (§5.3) y actualiza
  docs/estado-proyecto-homelab.md cuando confirmes un cambio real de
  contract_status_label (¡OJO, ver aviso siguiente!).

  TRAMPA CONOCIDA: `mission.status` (GET /api/missions/{id}) puede decir
  "completed" SIN que haya liquidación real. Eso solo significa que
  todos los nodos del DAG terminaron su trabajo, no que el contrato se
  resolvió on-chain. La señal fiable es SIEMPRE:
      GET /api/missions/{id}/onchain → contract_status_label
      (debe dejar de ser "InProgress", pasar a "Resolved"/"Completed")
  o settled_node_id / settle_tx_hash no nulos. Detalle en
  docs/playbook-api-completo.md § "Actualización 2026-08-03".

10. AUTOMATIZACIÓN / VIGILANCIA DIARIA
================================================================================

En este entorno de desarrollo se usó una Routine programada (cron
`13 9 * * *`) que revisa los Fallos B y D cada día y auto-completa la
misión en cuanto alguno se recupera (ver prompt exacto y lógica completa
en el historial de commits / docs/estado-proyecto-homelab.md §12). En tu
homelab, replica esto con un systemd timer o cron job — ejemplo completo
en docs/guia-homelab.md § "systemd timer".

Lógica mínima que debe tener el chequeo diario:
  1. curl a actions/complete/payload de una misión de prueba tuya →
     200 = Fallo B recuperado.
  2. curl a /api/dev/settlement/{missionId}/journal de una misión con
     nodos ya en Completed → step:"settle_submitted" = Fallo D
     recuperado.
  3. Si ambos siguen fallando: no hacer nada, salir en silencio.
  4. Si alguno se recupera: reautenticar wallets (tokens caducan),
     relanzar el script correspondiente, regenerar trazabilidad,
     comitear.

11. QUÉ NO INTENTAR "ARREGLAR" (SON FALLOS DE BACKEND, NO TUYOS)
================================================================================

  - No intentes parchear/reintentar infinitamente actions/complete
    (Fallo B) — es 500 del servidor, no hay nada que el cliente pueda
    hacer distinto.
  - No intentes registrar tú mismo un chain_node_id — no existe ningún
    endpoint/tool que lo permita; es un worker interno de AgentCity.
  - No confundas mission.status:"completed" con liquidación real (ver
    trampa en §7).
  - No asumas que el sistema de colaboración (§6, Sistema A) es un bug
    tuyo si se queda atascado en "executing" — es una trampa conocida de
    la plataforma si llamas route_node_task antes de cerrar la puja
    (close_node_bidding force=true SIEMPRE antes de route_node_task).
  - No gastes tiempo en Investment Vault (Fallo C), gobernanza NeurIPS
    completa (requiere rol admin + 5000 de stake) ni SDK Compatibility
    (requiere secreto HMAC del despliegue) contra el backend público —
    solo son viables con tu propio backend (§12).
