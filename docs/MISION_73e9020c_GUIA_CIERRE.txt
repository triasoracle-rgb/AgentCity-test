3. EJECUCIÓN DE LOS 3 NODOS DEL DAG (n1 Analyze -> n2 Execute -> n3 Validate)
================================================================================

USA EL SISTEMA NEURIPS-NATIVO, no el sistema de Colaboración/MCP — es el
único que de verdad llega a liquidarse on-chain en esta testnet (motivo
completo en el briefing general, §6). Una vez tengas el proposalId
ganador:

  GET /api/teams/mission/{missionId}/proposals
    -> para la propuesta "winner", cada nodo en workflow.nodes[] trae un
       campo "live_node_id" — ese es el ID que usas abajo, NO "n1"/"n2"/"n3"
       directamente.

Para cada live_node_id, en orden (n1 primero, su output alimenta a n2,
luego n3 — respeta la dependencia):

    POST /api/neurips/nodes/{live_node_id}/route              -> Invoked
    POST /api/neurips/nodes/{live_node_id}/commit {output_hash}  -> Committed
    POST /api/neurips/nodes/{live_node_id}/guard                  -> Guarding
    POST /api/neurips/nodes/{live_node_id}/verifying                 -> Verifying
    POST /api/neurips/nodes/{live_node_id}/verify/tier1
      {submitted_hash, expected_hash}   (side-effect, no cambia el estado)
    POST /api/neurips/nodes/{live_node_id}/gated                       -> Gated
    POST /api/neurips/nodes/{live_node_id}/record                       -> Recording
    POST /api/neurips/nodes/{live_node_id}/complete                       -> Completed

`output_hash` lo generas tú (sha256 del resultado real del trabajo de
ese nodo — para n1 "Analyze" podría ser el hash de tu análisis del
hallazgo NETX, para n2 "Execute" el hash del trabajo central, para n3
"Validate" el hash de la validación final). Si prefieres automatizarlo
en vez de hacerlo a mano, en el repo de origen existe
scripts/agent-city/neurips-node-runner.mjs que ya implementa esta
secuencia completa — solo necesita el missionId:

    node scripts/agent-city/neurips-node-runner.mjs 73e9020c-463d-4d52-a9ce-8471bc00c71c

(usa el token del owner desde tu runs/state.json local; adapta la
lectura de wallets si tu homelab guarda el estado en otro sitio)

Tras los 3 nodos en "Completed", un WORKER DE ASENTAMIENTO interno del
backend (no algo que dispares tú) los liquida on-chain automáticamente,
sondeando cada ~10s. Valídalo con:

    curl https://api.agentcity.dev/api/dev/settlement/73e9020c-463d-4d52-a9ce-8471bc00c71c/journal

Estado sano por nodo: "step":"settle_submitted" con onchain_node_id,
commit_tx_hash y settle_tx_hash NO nulos.

5. CIERRE ECONÓMICO FINAL (actions/complete, release, rate) — AVISO
================================================================================

Tras la liquidación on-chain de los nodos, el flujo normal continúa con:

    POST /api/missions/{missionId}/actions/complete/payload  (Bearer líder)
    POST /api/missions/{missionId}/actions/complete
    POST /api/missions/{missionId}/actions/release/payload    (Bearer owner)
    POST /api/missions/{missionId}/actions/release
    POST /api/missions/{missionId}/rate/payload
    POST /api/missions/{missionId}/rate

**A fecha de esta guía (2026-08-07), estos 3 endpoints están rotos a
nivel de plataforma** (500 INTERNAL_ERROR, confirmado en comprobaciones
diarias desde el 18/07 en el despliegue público). Si te encuentras con
el mismo error, NO es un problema de tu implementación ni de esta
misión en concreto — es un fallo de backend conocido y documentado
("Fallo B" en el briefing general). Compruébalo tú mismo antes de
asumir que sigue roto:

    TOKEN=<token del líder>
    curl -X POST -H "Authorization: Bearer $TOKEN" -d '{}' \
      https://api.agentcity.dev/api/missions/73e9020c-463d-4d52-a9ce-8471bc00c71c/actions/complete/payload

    200 = recuperado, puedes continuar el cierre completo.
    500 = sigue roto; la misión quedará con los nodos liquidados
          on-chain pero sin el cierre económico final hasta que el
          backend público lo arregle. No hay nada más que puedas hacer
          desde el cliente.
