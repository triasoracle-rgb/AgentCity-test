# AgentCity Mission Flow — Run Report (2026-07-27)

Reviewed `https://agentcity.dev/skills.md` and its linked documentation
(`llms.txt`, `llms-full.txt`, `skill.md`, `backend_skill.md`, per-topic docs
under `/llms/docs/`) to extend `mission-flow.mjs` and
`.claude/skills/mission-skill/SKILL.md` past collaboration-open into
workflow execution, on-chain completion, fund release, and rating —
capabilities `backend_skill.md` documents as steps 13–18 of its reference
script but that were missing from our implementation.

## What was added

- **Workflow execution**: `GET .../workflow/components` then
  `PATCH .../{id}/start` and `PATCH .../{id}/complete` for each component,
  run as the winning leader.
- **On-chain completion**: `POST /api/missions/{id}/actions/complete/payload`
  → sign EIP-712 → `POST .../actions/complete` (provider/leader-only).
- **Fund release**: same pattern with `actions/release` (client/owner-only).
- **Rating**: `POST /api/missions/{id}/rate/payload` → sign → `POST .../rate`,
  submitted by both the owner and the leader.
- **Reputation check**: `GET /api/delegate-agents/{id}/reputation` for both.

All five steps were added as best-effort (matching the pattern already used
for the agreement/payment phase) so a failure in this tail doesn't block the
rest of the flow or corrupt state for a later retry.

## Live test result (mission 676068cc, already in_progress from 2026-07-26)

- **Workflow execution: succeeded.** All 3 components reached `done`
  (`Plan and acceptance criteria`, `Execute mission`, `Verify and hand
  off`). Completing the last component **auto-advanced the mission's
  off-chain record straight to `status: completed`** — a lifecycle
  shortcut not documented in either skill.md or backend_skill.md, which
  both describe an intermediate `review` status.
- **On-chain completion: blocked.** `actions/complete/payload`,
  `actions/release/payload`, and `rate/payload` all returned
  `{"error":{"code":"INTERNAL_ERROR",...}}` for every role tried (leader,
  owner). This is a **new backend fault, distinct from the chain-service
  outage that recovered on 2026-07-26** — that recovery fixed
  `signing-payload` and `eip712-payload` but not this action/rating payload
  builder.
- **Consequence**: the mission contract on-chain remains
  `contract_status_label: InProgress` (unchanged since deployment at block
  780295) and the leader's wallet balance is unchanged — the off-chain
  "completed" status does **not** imply the escrow was released. Anyone
  reading only `GET /api/missions/{id}` would incorrectly conclude
  settlement finished; `GET /api/missions/{id}/onchain` is the source of
  truth and still shows `InProgress`.

```json
{
  "actionComplete": { "ok": false, "error": "HTTP 500 ... actions/complete/payload: INTERNAL_ERROR" },
  "actionRelease": { "ok": false, "error": "HTTP 500 ... actions/release/payload: INTERNAL_ERROR" },
  "onchain": { "contract_status_label": "InProgress", "block_number": 780295 }
}
```

Reputation lookups did succeed (both agents show `average_score: 500`
default, `total_missions_completed: 0`, `onchain_rating_count: 0` —
consistent with no rating or release ever having landed on-chain).

## Documentation gaps found vs. live API

- `skill.md`'s "Typical completion flow" names the actions `submit` and
  `approve`; the live API rejects both with `Unknown action`. The correct
  names, confirmed against the live OpenAPI schema and role-permission
  errors, are `complete` (provider-only) and `release` (client-only),
  matching `backend_skill.md` instead.
- `skill.md`'s "Blockchain Details" table lists contract addresses that do
  not match the live `GET /api/config` response for this deployment — a
  reminder (which the docs themselves also state) to always read addresses
  from `/api/config` at runtime rather than from prose.
- Completing the last workflow component transitions the mission straight
  to `completed` off-chain, skipping the documented `review` intermediate
  status.
